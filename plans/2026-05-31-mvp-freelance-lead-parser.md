## Цель (что должно работать к концу)

Личный Telegram-парсер фриланс-заказов, который **без ручного дежурства**:

- слушает 13 заданных чатов от лица аккаунта Давида (Telethon user-session);
- ловит релевантные посты по словарю айтишных ключевиков, отсекает
  минус-слова («за отзыв», «бесплатно», «студент» …);
- шлёт релевантный пост Давиду в личку бота **за ≤5 минут** от публикации,
  со ссылкой на исходное сообщение;
- не присылает дубли (тот же пост; тот же текст в другом чате в течение
  30 минут).

«Готово» по разделу 8 спеки в рамках этой итерации (по решению Давида —
**локально + готовность к деплою**, сам деплой на VPS отдельным шагом):

- сервис слушает ≥3 чата и реагирует на новое сообщение;
- релевантный пост → приходит в личку ≤5 мин со ссылкой;
- нерелевантный (нет ключевика / есть минус-слово) — не приходит;
- дубль — повторно не приходит;
- все секреты в `.env`; старый bot-токен из образца отозван, вписан новый;
- `README.md` (что это, запуск, env-vars, как добавить чат/ключевик/минус-слово);
- первый git-коммит сделан;
- systemd-юнит и инструкция по деплою готовы (но сам деплой — позже).

## Гипотезы (что предполагаем — может оказаться неправдой)

- **Г1.** Аккаунт сессии (`TELEGRAM_SESSION`) реально состоит во всех 13
  чатах и Telethon видит их события. Если из какого-то чата событий нет —
  аккаунт туда не добавлен / чат недоступен.
- **Г2.** `event.chat_id` у Telethon приходит в том же формате `-100…`,
  что и список `SOURCE_CHATS`. Для каналов/супергрупп — да; если для
  части источников формат иной, фильтр их пропустит молча (проверить на
  прогоне, логировать «событие из чата X»).
- **Г3.** Фильтр по ключевикам с границей слова даёт точность ≥70%.
  Это гипотеза — словарь и минус-слова почти наверняка придётся
  подкручивать после недели наблюдения (на то и метрика точности).
  **Отдельно про полноту (recall):** точный матч по словоформе мимо
  русских склонений («парсера», «бота», «спарсить» при базовом «парсер»/
  «бот»). Пропущенный заказ дороже лишнего уведомления, поэтому словарь
  засеваем основными словоформами, а для безопасных корней (без коллизий)
  разрешаем префиксный матч. Это осознанный компромисс precision↔recall,
  а не «подкрутить потом» (см. правку П4 в Фазе 2).
- **Г4.** Бот сможет писать Давиду в личку после **одного** ручного
  `/start` у бота, а `MY_TELEGRAM_ID` — верный числовой id. Без `/start`
  Telegram запрещает боту инициировать переписку.
- **Г5.** Для дедупа достаточно одной SQLite-таблицы и одного процесса
  (нет конкурентного доступа). Postgres из образца — избыточен.
- **Г6.** `get_sender()` обычно отдаёт `author_id`. Для постов «от имени
  канала» автор может быть `None` — дедуп №2 тогда работает по
  `(fingerprint, author=None)`, это допустимо.
- **Г7 — снято (план3, правка П1).** Проверено по образцу: `parsing/matching.py`
  уже нормализует **и текст, и ключевик** симметрично (строка 31), поэтому
  `telegram-бот`, `make.com`, `n8n`, `api интеграция` матчатся без правок.
  Исходная гипотеза была основана на неверном прочтении образца — никакой
  «правки относительно образца» в матчинге не требуется.

## Технические решения (через что и почему)

- **Язык/стек:** Python 3.12, Telethon (слушатель от лица аккаунта),
  aiogram (только отправка боту — без polling, UI-настроек нет).
  Совпадает со спекой §5 и образцом.
- **Хранилище — `sqlite3` из стандартной библиотеки, без SQLAlchemy.**
  Сознательное упрощение относительно образца: нужна одна таблица для
  дедупа (спека §5 — «нужна **одна** таблица»), ORM и пул соединений тут
  лишние. Меньше зависимостей, проще деплой. Если вернётся мультиюзер —
  мигрируем на Postgres+SQLAlchemy (как в образце).
- **Конфиг в коде, не в БД и не в `.env`:**
  - `SOURCE_CHATS` (13 marked-id из спеки §6) — список в `config.py`.
    Таблицу `source_chats` из образца **не делаем** (иначе таблиц две, а
    спека требует одну). Это и есть фильтр: событие из чата не из списка → skip.
  - `KEYWORDS` (словарь категорий) и `MINUS` (минус-слова) — в `keywords.py`
    из спеки §6. README объяснит, как править эти списки.
  - В `.env` только секреты (спека §6 их и перечисляет): `API_ID`,
    `API_HASH`, `TELEGRAM_SESSION`, `BOT_TOKEN`, `MY_TELEGRAM_ID`.
- **Дедуп — два уровня в таблице `seen`** (схема из спеки §6):
  `seen(fingerprint, chat_id, message_id, author_id, created_at)`.
  1. точный: видели `(chat_id, message_id)` → skip;
  2. cross-chat: тот же `fingerprint(text)` + `author_id` за последние
     30 минут → skip.
  `fingerprint` = md5 от `text.lower().strip()` (берётся из образца как есть).
  - **Правка П2 (NULL-author).** Образец на SQLAlchemy сам превращает
    `author_id == None` в `IS NULL`. Голый `sqlite3` так НЕ умеет:
    `WHERE author_id = ?` с параметром `None` → `= NULL` → всегда ложь,
    и дедуп №2 для постов «от имени канала» (автор `None`, это Г6) тихо
    перестаёт ловить дубли. Поэтому условие пишем явно:
    `(author_id = ? OR (? IS NULL AND author_id IS NULL))`.
  - **Правка П11 (время).** `created_at` храним как **unix-epoch int (UTC)**,
    не строку — сравнение окна «30 минут» на ISO-строках коварно (формат,
    таймзоны). Образец живёт в UTC через `datetime.now(timezone.utc)` —
    эту дисциплину сохраняем.
- **Матчинг (перенос `parsing/matching.py` практически как есть, правка П1):**
  `normalize()` → lower, `ё→е`, убрать пунктуацию, схлопнуть пробелы.
  `extract_category(text)` идёт по `KEYWORDS`, нормализуя **и текст, и
  ключевик** (образец это уже делает — `matching.py:31`, правка «симметрии»
  НЕ нужна), матч по границе слова (`f" {kw} " in f" {text} "`) — это режет
  ложные срабатывания на подстроках. `has_minus(text)` — если есть любое
  минус-слово, пост отбрасывается **до** проверки ключевиков.
  - **Правка П4 (recall на словоформах):** базовый словарь засеваем
    основными словоформами; для безопасных корней без коллизий разрешаем
    префиксный матч, чтобы не терять склонения. Осознанный компромисс
    precision↔recall (см. Г3).
- **Ссылка на пост (расширяем `lead_link_service.py`):** в collector берём
  сущность чата; если у неё есть `username` → публичная ссылка
  `https://t.me/<username>/<message_id>`; иначе → приватная
  `https://t.me/c/<internal_id>/<message_id>`, где `internal_id` —
  `chat_id` без префикса `-100`. (Образец умел только приватную форму.)
- **Отправка:** `aiogram.Bot.send_message(MY_TELEGRAM_ID, text,
  parse_mode=HTML)`. Текст обрезаем под лимит Telegram 4096. Формат
  сообщения (перенос `lead_formatter.py`): эмодзи-заголовок, найденная
  **категория** (чтобы Давид на глаз оценивал релевантность и точность),
  фрагмент текста заказа, кликабельная ссылка.
- **Устойчивость (с правкой П6):** reconnect-loop из образца — `while True:
  try client.start()/run_until_disconnected() except: sleep(5)`. **Но**
  разделяем ошибки: транзиентная сетевая → retry со `sleep(5)`; ошибка
  авторизации (`AuthKeyError`/`Unauthorized` — отозванная/протухшая сессия)
  → понятный лог + **выход с кодом ≠0**, чтобы systemd показал `failed`, а
  не крутил молча. Иначе сервис «работает», а уведомлений нет. Не-текстовые
  и пустые сообщения → skip.
- **Логирование (правка П8):** минимальный `logging` в stdout с уровнем и
  таймстемпом (journald заберёт под systemd). Настройка инлайн в `main.py`
  (отдельный `logging_config` из образца не тащим — оверкилл для MVP).
- **Что срезаем из образца целиком:** `User`/`Payment`/`LeadDelivery`/
  `ContactOpen`, `services/matching_service.py`, `services/dispatch_service.py`,
  метро/районность (`extract_metro`, `metros.py`), весь `bot/` и
  `telegram_ui/` (UI подписок), Postgres-слой `database/`.
- **Безопасность (спека §6, §8):** `.env` сразу в `.gitignore`; `.env` не
  читаем и не коммитим; в коде только `os.environ[...]`. Bot-токен из
  образца считаем скомпрометированным — старый отозвать у @BotFather,
  в `.env` вписать новый. Файл `Информация по проекту.txt` из образца —
  источник боевых секретов, в код не переносится.
- **Структура проекта (плоская, модульная, в стиле Давида —
  баннер-комментарии, разбивка, type hints):**
  ```
  freelance-lead-parser/
  ├── .env                 (Давид заполнит; в .gitignore, не коммитим)
  ├── .env.example         (имена переменных без значений)
  ├── .gitignore           (.env, *.session, *.db, __pycache__)
  ├── requirements.txt     (telethon, aiogram, python-dotenv)
  ├── README.md
  ├── config.py            (load_dotenv, секреты, SOURCE_CHATS)
  ├── keywords.py          (KEYWORDS + MINUS)
  ├── fingerprint.py       (md5-отпечаток)
  ├── matching.py          (normalize, extract_category, has_minus)
  ├── link.py              (build_link: public / private)
  ├── formatter.py         (format_message)
  ├── db.py                (sqlite3: init seen, is_duplicate, mark_seen)
  ├── collector.py         (Telethon listener + обработка + отправка)
  ├── main.py              (настройка logging → init db → run collector)
  ├── generate_session.py  (генератор StringSession, разовый)
  └── deploy/
      └── freelance-lead-parser.service  (systemd-юнит, шаблон под VPS)
  ```

### Фаза 2 — Ядро фильтрации, offline `[x]` (шаги 3, 4 частично)
`keywords.py` (`KEYWORDS` + `MINUS` из спеки §6, **засеять словоформами —

**Результат (проверяемо):** на наборе примеров релевантный текст отдаёт

### Фаза 3 — Дедуп, offline `[x]` (шаг 5)
`db.py` на `sqlite3`: создание таблицы `seen(fingerprint, chat_id,
message_id, author_id, created_at)`, где `created_at` — **unix-epoch int в
UTC (правка П11)**; `is_duplicate(...)` — оба уровня (точный по
`(chat_id, message_id)` и cross-chat по `(fingerprint, author)` за 30 минут).
**Cross-chat-условие пишем с явной обработкой NULL (правка П2):**
`(author_id = ? OR (? IS NULL AND author_id IS NULL))` — иначе для постов
«от имени канала» (автор `None`, Г6) дедуп №2 молча течёт. `mark_seen(...)`.
**Результат (проверяемо):** на временной БД повтор `(chat_id, message_id)`
ловится; тот же текст в другом чате за <30 мин ловится; он же спустя
>30 мин проходит; **дубль с `author_id = None` тоже ловится (проверка П2)**.
Offline.

### Фаза 5 — Конфиг и секреты `[x]` (шаг 2)

**`MY_TELEGRAM_ID` привести к `int` (правка П10)** — `os.environ` отдаёт

(`.env` заполняет Давид — см. пред-условия.)

### Фаза 6 — Генерация Telethon-сессии `[x]` (шаг 8, совместно с Давидом)
`generate_session.py` — разовый генератор `StringSession`: логин по
номеру/коду телефона Давида, печать строки сессии.
**Результат (проверяемо):** скрипт запущен **вместе с Давидом**, он
залогинен, полученный `TELEGRAM_SESSION` вписан в `.env`. Требует
операционных пред-условий Давида (токен, `/start`).

### Фаза 7 — Слушатель `[x]` (шаги 6, 7)
`collector.py` — Telethon listener. **Фильтр на уровне подписки (правка П7):**
`@client.on(events.NewMessage(chats=SOURCE_CHATS))` вместо фильтра-в-хендлере —
тогда `get_sender()` не дёргается на чужих чатах (меньше сетевых вызовов →
меньше шанс FloodWait). **Логику обработки одного сообщения выносим в
отдельную функцию** `process_message(text, chat_id, msg_id, author_id, entity)`,
не завязанную на Telethon, чтобы гонять её offline синтетическими событиями
(оркестрация: `has_minus` → skip; нет категории → skip; дедуп оба уровня →
skip; собрать ссылку; обрезать ≤4096; вернуть готовое сообщение). Тонкий
Telethon-адаптер только распаковывает `event` и зовёт `process_message`,
затем `aiogram` шлёт в `MY_TELEGRAM_ID`. Лог «событие из чата X» — проверка Г2.
**Reconnect-loop с правкой П6:** транзиентная сетевая → retry `sleep(5)`;
auth-ошибка (`AuthKeyError`/`Unauthorized`) → понятный лог + выход с кодом ≠0.
Логирование в stdout (правка П8). `main.py` — настройка `logging` → init БД →
запуск collector.
**Результат (проверяемо):** `process_message` проходит offline-тесты на
синтетических событиях (минус-слово / нет категории / дубль / релевант)
**без Telegram (проверка П7)**; `python main.py` подключается без падения,
логирует входящие события из заданных чатов, на тестовое релевантное
сообщение шлёт личку боту; при битой сессии — внятный лог и выход, а не
тихий цикл (проверка П6). Зависит от фаз 2–6.

### Фаза 8 — Локальный прогон по критериям §8 `[x]` (шаг 11)
End-to-end проверка приёмки спеки. **Управляемый тест-путь (правка П5):**
чтобы приёмка не зависела от органического трафика в чатах, гоняем через
тест-группу Давида `-5024560890` — Давид сам постит туда тестовые сообщения
(релевант / минус-слово / дубль) и смотрит реакцию по требованию.
- **Важно:** id `-5024560890` идёт **без** префикса `-100` (basic-группа, не
  супергруппа) — на время прогона добавить его в `SOURCE_CHATS`; это заодно
  живая проверка Г2 (другой формат `chat_id`). После прогона можно убрать.
Критерии: ≥3 чата реагируют; релевантный пост приходит в личку ≤5 мин со
ссылкой; нерелевантный (нет ключевика / есть минус-слово) — не приходит;
